# Estabilidade da leitura de produtos (ordem determinística, sem fallback de seed, histórico)

- status: implemented 2026-11-25
- requested: 2026-11-25 · by: Patrick (incidente 2026-11-24→25)

## Goal
Acabar com os três efeitos do incidente de 2026-11-24→25. (a) Na lista de produtos do admin, apareciam produtos duplicados ou em falta entre páginas: `readProductsPage` ordena só por `updated_at desc` com `.range()`, e um UPDATE em massa via SQL deu o mesmo `updated_at` a cerca de 133 linhas. (b) No catálogo público apareciam produtos antigos e "alterações revertidas": `readProducts`/`readProductById` caem para o seed local (`getCmsProducts`) em caso de erro, timeout ou resultado admin vazio, e `/api/shop/catalog` (force-static, revalidate 86400) e os PDPs ISR colocam esse seed em cache. (c) Não existia rasto de quem alterou o quê: alterações feitas pelo SQL editor não passam pela app.
Correções:
1. desempate por `id` em todas as ordenações e paginações de `cms_products`;
2. com Supabase configurado, a leitura pública nunca serve nem coloca seed em cache. Se a leitura falhar, lança erro: o ISR mantém a última versão boa e o cliente mostra um estado de erro com "Retry". O seed fica apenas para dev local sem Supabase;
3. log estruturado nas falhas e timeouts, mais uma tabela `cms_products_history` preenchida por trigger.

## Contrato partilhado (fixado antes dos builders arrancarem, permite trabalho em paralelo)
- Quando `isSupabaseConfigured()` é verdadeiro, `readProducts(...)`, `readProductById(...)` e `readProductSkuIndex(...)` **lançam `CmsReadError`** (de `src/lib/cms/server/strict-read.ts`) em erro ou timeout. Já não devolvem seed. Com Supabase não configurado, o comportamento mantém-se (seed/ficheiro local).
- `readProducts` aceita uma nova opção opcional `source?: string` (ex.: `"api/shop/catalog"`), usada apenas no log. Também `readProductById(id, { asAdmin, source })`.
- Um resultado vazio do Supabase é um resultado válido (`[]`). Deixa de existir o ramo `products.length === 0 && asAdmin → seed`.
- Ordem canónica da lista: `updated_at desc, id asc`. É sempre determinística, com ou sem `.range()`.

### Query pronta para ler o histórico (SQL editor / service role)
```sql
-- Últimas alterações de um produto (por id ou sku), com email do autor quando existir
select h.changed_at, h.op, h.product_id, h.sku, h.changed_columns,
       h.old_values, h.new_values,
       coalesce(u.email, case when h.jwt_role is null then 'SQL editor (' || h.db_session_user || ')' else h.jwt_role end) as actor,
       h.tx_id
from public.cms_products_history h
left join auth.users u on u.id = h.actor_uid
where h.product_id = :'product' or h.sku = :'product'
order by h.changed_at desc, h.id desc
limit 100;

-- Updates em massa: transações que tocaram muitos produtos nas últimas 48h
select tx_id, min(changed_at) as at, count(*) as rows, jwt_role, db_session_user,
       array_agg(distinct c) as columns
from public.cms_products_history, unnest(changed_columns) c
where changed_at > now() - interval '48 hours'
group by tx_id, jwt_role, db_session_user
having count(*) > 10
order by at desc;
```

## Risks / notes
- **Security-reviewer obrigatório**: a migração nova em `supabase/` (tabela, RLS, função SECURITY DEFINER, grants) e as alterações em `src/app/api/cms/**` e `src/app/api/shop/**`. Pontos a verificar: `search_path` fixo na função; nenhum `execute` concedido a `anon`/`authenticated`; policy de select apenas `super_admin`/`admin` via `cms_has_role`; o histórico pode conter preços e dados de produto não publicados (rascunhos), por isso **não** deve ser legível pelo cliente público; `detail` nos logs não expõe mensagens do Postgres com dados de linha; `readFailureResponse` mantém a mensagem genérica.
- **Comportamento novo em falha**: sem seed, uma falha do Supabase no **build** (primeiro render de `/api/shop/catalog`, `sitemap.ts`) faz falhar o build. Isto é intencional e já acontecia com a guarda de catálogo vazio: o deploy anterior mantém-se. `src/app/sitemap.ts` não muda de código, mas passa a lançar erro em vez de listar o seed. Se não houver cache, o PDP mostra `error.tsx` em vez de dados antigos.
- **Limite de linhas do PostgREST**: `readProducts` faz um único SELECT sem `.range()`. Se `cms_products` ultrapassar o `max-rows` do projeto (por omissão 1000), o resultado é truncado. Com a nova ordem, o truncamento passa a ser determinístico, mas continua a existir. Verificar `select count(*) from cms_products`. Follow-up: paginar `readProducts` como `readAllRowsStrict`.
- **Peso do trigger**: um update em massa de N linhas gera N inserts no histórico, mais uma subtransação por linha (bloco `exception`). Para cerca de 1–2k produtos é aceitável. Guardar só as colunas alteradas e um md5 para `description` mantém as linhas pequenas.
- **Retenção**: automática, 180 dias. `public.cms_products_history_purge(retention_days int default 180)` (SECURITY DEFINER, mínimo 30 dias, só `service_role`) é chamada diariamente (`0 5 * * *`) por `src/app/api/cron/purge-product-history` (CRON_SECRET). O `service_role` continua sem `delete` na tabela. Requer security-reviewer.
- **Relação com `cms_audit_logs`**: o audit log da app só regista ações feitas pela app. O histórico por trigger cobre também o SQL editor e o service role, que foi a lacuna do incidente. Não substitui o audit log.
- **Follow-ups (fora de âmbito)**: UI admin para ver o histórico por produto (aba no editor), com reutilização das queries acima via rota `api/cms` guardada por `cmsGuard`; paginação de `readProducts`.
- **Deploy**: a migração tem de ser aplicada em produção junto com o deploy (acrescentar à lista "Prod pending SQL"). A app não depende da tabela para funcionar: se a migração estiver por aplicar, só não há histórico. Nunca fazer commit/push para `main` sem aprovação explícita.
