# Global-presence map: overseas companies, registered address, email/phone toggles

- status: done
- requested: 2026-10-26 · by: Patrick (via orchestrator)

## Goal
Put the overseas company list (company name + registered address only, from "Overseas Company list 260916.xlsx"; row 22 Agrichip is skipped) on the public global-presence map on /about. Editing happens at /admin/global-presence/map. Empty fields never render. Each office gets a `registeredAddress` field (localized textarea) and two booleans, `showEmail` and `showPhone`. Both default to true and every public consumer respects them. Hidden values are removed in the resolve step and in the public GET response. Data loading works as "pre-load, user reviews, user saves": a seed file plus an "Import overseas companies" button in the admin editor merge the seed into the editor's unsaved state, and the user then clicks the existing Save. Production rows in Supabase are never edited by hand. The local fallback `data/map-locations.json` gets the same merge.

## Findings that shape the plan
- `GET /api/map-locations` has no auth. Two clients read it: the admin editor (`MapLocationEditor.tsx:53`) and the shop hook (`src/lib/shop/use-map-locations.ts:17`). If that GET strips hidden values, the admin editor loses them and the next Save overwrites them. So the admin editor must load from a new authenticated route `GET /api/cms/map-locations`, and the public GET always strips. PUT stays where it is.
- `map_locations_config` has an RLS policy `"Public read map config"` that lets `anon` select the whole row (`supabase/schema.sql:11`). The raw blob, hidden contacts included, can therefore be read straight from PostgREST with the public anon key. See Risks.
- `src/lib/shop/office-resolver.ts` and `use-map-locations.ts` import `data/map-locations.json` statically, so the fallback file ships in the client JS bundle.
- QuoteModal and CheckoutPage only use `office.officeId`. `OfficeCard.tsx` is the only shop component that renders email/phone, and it reads them through `toResolvedOffice` → `ResolvedMapOffice`. Stripping in `resolveMapLocationsForLocale` covers it. Server code never uses office email/phone (`api/shop/rfq` only checks office ids).
- `primaryOfficeId` references exist (`data/shop/countries.json`: `usa-office`, `brazil-office`, `mexico-office`, `norway-office`, `china-office`, `england-office`, plus the Supabase marketplace config). So do `/contact?office=<id>` links. Deleting placeholder offices would break these unless the ids are reused (merge rule M3 below).
- `NL` is missing from `countryFlagOptions` in `src/constants/country-flags.ts`. Without it, `validateMapLocations` rejects flag "NL" and `CountryFlag` renders nothing. `country-flag-icons` already includes NL, so no new dependency is needed.
- `MapLocationInfoPanel` is the only public renderer (GlobalPresence/InteractiveWorldMap render no office fields). The admin preview also uses it via `resolveMapLocationsForLocale`, so the preview will match the public result.
- Next.js: this only uses standard route handlers (`GET`/`PUT` in `route.ts`) and no new Next API. The new cms route is dynamic because `cmsGuard` reads cookies.

## Merge rules (pure function `mergeOverseasCompanies(data, seed)`)
- M1. Group seed companies by `locationId`. Locations with no seed company (mexico, argentina, ethiopia, china, singapore) are returned unchanged, deep-equal to the input.
- M2. If the location `netherlands` is missing, create it: `id "netherlands"`, `flag "NL"`, `hasFactories false`, `sendOnly false`, x ≈ 382, y ≈ 88 (between england 368.15/98, norway 394.64/64.89 and poland 410.53/84.76; the user can drag it). Country names: en "Netherlands", pt-BR "Países Baixos", es "Países Bajos", zh-CN "荷兰". Start it with no offices; the seed fills them.
- M3. In each seeded location, remove offices whose `email` ends with `@oboya.example` (case-insensitive), in order. To keep `primaryOfficeId` and `?office=` links working, the n-th newly added seed office takes the id of the n-th removed placeholder. Seed offices beyond that get `slugifyId(\`${locationId}-${companyName}\`, existingIds)`.
- M4. Keep every other existing office untouched.
- M5. Add a seed office only if no remaining office in that location has a matching `company` (trimmed, case-insensitive, compared in any locale).
- M6. Shape of a seeded office: `email ""`, `showEmail true`, `showPhone true`. For all four locales, `company`, `city` and `registeredAddress` come from the seed and are identical across locales; every other field is `""`.
- M7. Idempotent: `merge(merge(d, s), s)` deep-equals `merge(d, s)`. Return a summary `{ added, removedPlaceholders, createdLocations }` for the UI notice.
- M8. Never store or read any other seed property (tax ID, licence, legal rep, incorporation date, shareholders). The seed loader whitelists `locationId`, `company`, `city` and `registeredAddress`. `row` is allowed but not copied into map data.

## Risks / notes
- **Security review required.** This touches API routes (`src/app/api/map-locations`, new `src/app/api/cms/map-locations`) and the data path behind auth (the new route uses `cmsGuard`). The PUT guard must stay `cmsGuard("global_presence", "edit")`.
- **"Hide" is not confidential.** RLS on `map_locations_config` allows `anon` to select the full row, so hidden email/phone can still be read from Supabase directly with the public anon key. In no-Supabase mode they also ship in the client bundle through the static import of `data/map-locations.json`. The toggles control presentation only. Making hidden contacts truly private would need a separate RLS-protected column or table plus a migration, which is out of scope. Tell the user, and do not put anything sensitive in those fields. The same reasoning is why decision 1 keeps tax ID, licence and similar data out entirely; M8 enforces it.
- **Office id reuse (M3)** is an implementation detail that keeps existing `primaryOfficeId` values (local `countries.json` and the Supabase marketplace config) and `/contact?office=` links valid. Without it, the shop would silently fall back to `offices[0]` and the currencies admin would warn "unknown primary office".
- **Netherlands x/y** are estimates; the user should drag the marker into place before saving. The new location gets arrows automatically through `map-connections` unless `sendOnly` is set.
- **Rule 7:** `MapLocationEditor.tsx` is touched by builder-admin only, in tasks 4 and 5 in sequence. `src/lib/map-locations.ts` and `src/constants/country-flags.ts` (shared) are touched by builder-site in task 1 only.
- **Unclaimed paths:** `src/app/api/map-locations/**` and `data/map-locations.json` are not in the Project map. They are assigned to builder-admin, since the admin editor is their only writer.
- **Migrations:** none. Production data changes only when the user clicks Import → reviews → Save in the admin. There is nothing to add to the prod-pending SQL handover.
